# Вимоги та бізнес правила системи списків покупок

**Проєкт:** Інтелектуальна система керування списком покупок.
**Команда:** Данченко Денис; Пархоменко Олександр.
**Версія:** `lab01-spec`, 19.11.2026.

Цей документ є єдиним джерелом істини для полів, валідації, станів, фільтрації та статистики. API і майбутні тести посилаються на наведені нижче правила. Позначення: U — вимога з повідомлення користувача; M — обмеження методички; D — проєктне уточнення для цієї версії. Проєктні уточнення наведені явно й можуть бути змінені командою до реалізації з узгодженим оновленням документів.

## 1 Межі системи

Користувач працює з локальною вебсистемою через REST API та сторінку документації API. У поточному обсязі є FR-01–FR-08, FR-09 розробляється в ЛР4. У ЛР1 реалізація API та запуск моделі не виконуються.

Обсяг не включає реєстрацію, ролі, спільні акаунти, ціни, бюджет, оплату, рецепти, історію покупок, видалення або перейменування списків, редагування довідника через API та зовнішні магазини. Двоє членів навчальної команди — автори проєкту, а не дві ролі продукту. Автентифікація для локального навчального прототипу не вводиться.

## 4 Контракт даних

Довжина рядків рахується в Unicode code points після зазначеної нормалізації, не в байтах. `strip()` видаляє крайні пробільні символи; внутрішні пробіли й регістр зберігаються. Порожній рядок після нормалізації — некоректний. Поля у JSON чутливі до регістру. Усі системні поля доступні лише у відповіді; передавання їх у тілі запиту відхиляється.

## 6 Бізнес правила

### BR-01 Створення та зв’язки

Нова позиція створюється лише в наявному списку, з наявною категорією та is_purchased=false. Клієнт передає name, quantity, unit, category_id. Id, list_id у body, created_at та is_purchased у Create заборонені. Порожній список є коректним. Позицію не можна прочитати, змінити або видалити через id іншого списку: повертається 404 item_not_found.

### BR-02 Стани покупки

| Поточний стан / Передане is_purchased | false — непридбано | true — придбано |
| --- | --- | --- |
| false — непридбано | 200 без зміни | 200, встановити true |
| true — придбано | 200, встановити false | 200 без зміни |

Усі чотири комбінації визначені. Невідомі значення, null та неправильні типи — 422. Для відсутньої позиції — 404. Повторне встановлення стану не створює нової позиції та не змінює created_at. На обох станах дозволені перегляд, редагування, видалення і повторна зміна стану. Відсутня після видалення позиція не є третім бізнес-станом.

### BR-03 Часткове редагування та атомарність

Дозволені поля звичайного PATCH: name, quantity, unit, category_id. Стан змінюється окремою операцією purchase.

| Випадок | Результат |
| --- | --- |
| Поле не передане | Поточне значення зберігається |
| Допустиме поле передане з коректним значенням | Змінюється лише воно |
| Будь-яке поле дорівнює null | 422; усі дані без змін |
| Порожнє тіло {} | 200 з поточною позицією; для відсутньої позиції 404 |
| Body відсутній або JSON не є об’єктом | 422 |
| Невідоме чи системне поле або is_purchased у звичайному PATCH | 422; поле не ігнорується |
| Є коректні та некоректні значення разом | 422; жодна зміна не зберігається |
| Зміна unit робить поточну quantity недопустимою | 422, якщо в тому самому запиті не передано коректну quantity |
| Передані значення збігаються з поточними | 200 без фактичної зміни |

Увесь новий об’єкт перевіряється до запису. Зміни й перевірка посилань виконуються як одна транзакційна операція; при помилці запису — rollback. Описана ідемпотентність стосується цих операцій присвоєння, а не всіх можливих PATCH загалом.

### BR-04 Фільтрація і порядок

GET списку допускає необов’язкові category_id та is_purchased. Якщо передано обидва, позиція повинна задовольняти обидві умови. Відсутній параметр не обмежує результат. У query стан має вигляд рівно true або false; 0, 1, True та null не приймаються. Невідома категорія дає 422. Порожній збіг — 200 з items=[]. Наявність списку перевіряється навіть при порожньому результаті.

Списки та позиції впорядковуються за (created_at ASC, id ASC), категорії — за id ASC. Невідомі або повторені query-параметри відхиляються з 422. Маршрути без query-параметрів не приймають їх.

### BR-05 Статистика

total_items — кількість позицій; purchased_items — кількість позицій з true; unpurchased_items — кількість з false. Завжди total_items = purchased_items + unpurchased_items. Для кожної категорії обчислюються ті самі три значення. Сума total_items за категоріями дорівнює загальному total_items, аналогічно для двох інших лічильників.

Статистика обмежена list_id, незалежна від фільтрів попереднього GET, містить всі 10 категорій у порядку id. Для порожнього списку всі значення — 0. Невідомий список дає 404, а не нульовий підсумок. Після успішного створення, редагування категорії, позначення або видалення наступний GET статистики бачить поточні дані. Підсумки не зберігаються окремо; один запит статистики читає узгоджений знімок даних.

### BR-06 Помилки та їх пріоритет

1. Перевірити JSON-форму, дозволені поля, типи, локальні межі path/query/body: 422. Для неподтримуваного Content-Type з тілом — 415.
2. Для коректного за формою запиту перевірити існування списку, потім належність позиції: 404.
3. Перевірити посилання на категорію та кінцеву пару quantity/unit: 422.
4. Виконати операцію атомарно. Неочікувана внутрішня помилка — 500 без часткового запису.

Тому структурно некоректний запит до відсутнього списку дає 422; структурно коректний запит із невідомою категорією до відсутнього списку спочатку дає 404. Тіло помилки визначене в API-контракті. 409 не вводиться штучно: в поточній моделі немає забороненого переходу між двома допустимими станами. Це адаптація прикладу до іншої предметної області.

### BR-07 AI рекомендація

У ЛР4 модель отримує name і фіксований довідник із описами, повертає category_id та коротке обґрунтування. Рекомендація не приймає команд на запис до БД. Для недостатньо визначеного тексту допустимий результат needs_clarification без категорії. Недоступність або некоректна відповідь моделі приводить до контрольованої помилки; ручний вибір залишається доступним. План порівняння з baseline наведено в розділі 9 цього документа.

## 7 User Stories та критерії приймання

AC описують спостережувану поведінку майбутнього API. Кожна поточна історія має позитивний та негативний або граничний критерій. Вісім історій відповідають восьми поточним FR; дев’ята відкладена до ЛР4.

### US-01 Створення списку — FR-01

Як користувач, я хочу створити іменований список, щоб окремо планувати покупки.

- **AC-01-01:** Given коректний запит з name="  На тиждень  ", When створюється список, Then 201, name="На тиждень", додатний id та UTC created_at; список доступний при перегляді.
- **AC-01-02:** Given name відсутнє, null або після strip порожнє, When надходить Create, Then 422 і новий список не з’являється.
- **AC-01-03:** Given назви довжиною 1 і 120 символів після strip, When Create, Then обидві приймаються; довжина 121 дає 422.

### US-02 Додавання позиції — FR-02

Як користувач, я хочу додати товар з кількістю, одиницею та категорією, щоб знати, що потрібно купити.

- **AC-02-01:** Given існує список 10 і категорія 1, When додати Молоко, quantity=2, unit=л, category_id=1, Then 201, is_purchased=false і позиція належить списку 10.
- **AC-02-02:** Given quantity=0 або невідомий category_id, When Create у наявному списку, Then 422 без нової позиції.
- **AC-02-03:** Given quantity=0.001 л або 10000 л, When Create з іншими коректними полями, Then 201; 0.0009, 10000.001, 1.2345 л та 0.5 шт дають 422.
- **AC-02-04:** Given список 999 відсутній, When структурно коректне додавання, Then 404 list_not_found.

### US-03 Перегляд — FR-03

Як користувач, я хочу переглядати списки та їхні позиції, щоб бачити заплановані покупки.

- **AC-03-01:** Given є два списки й позиції в кожному, When GET /lists та GET одного списку, Then повертаються списки та лише позиції вибраного списку у порядку BR-04.
- **AC-03-02:** Given списків немає або вибраний список порожній, When відповідний GET, Then 200 і [] для списків або items=[] для порожнього списку.
- **AC-03-03:** Given список відсутній, When GET за його id, Then 404.

### US-04 Редагування — FR-04

Як користувач, я хочу змінювати поля позиції, щоб уточнювати план покупок.

- **AC-04-01:** Given позиція має quantity=2, unit=л, category_id=1, When PATCH лише name, Then 200, name змінено, усі інші поля збережено.
- **AC-04-02:** Given наявна позиція, When один PATCH містить коректне name і quantity=0, Then 422; навіть name лишається попереднім.
- **AC-04-03:** Given наявна позиція, When PATCH з null або id, created_at, list_id, is_purchased чи невідомим полем, Then 422 без змін; коли PATCH={}, Then 200 без змін.
- **AC-04-04:** Given item належить іншому списку, When PATCH через поточний list_id, Then 404 і позиція не змінюється.
- **AC-04-05:** Given quantity=0.5 та unit=кг, When PATCH лише unit=шт, Then 422 без змін; PATCH quantity=2 і unit=шт одночасно успішний.

### US-05 Видалення — FR-05

Як користувач, я хочу видаляти непотрібні позиції, щоб список залишався актуальним.

- **AC-05-01:** Given позиція існує, When DELETE у її списку, Then 204 без тіла; наступний перегляд її не містить, лічильники статистики зменшено.
- **AC-05-02:** Given позиція вже видалена або належить іншому списку, When DELETE, Then 404; решта позицій не змінюється.

### US-06 Стан придбання — FR-06

Як користувач, я хочу позначати й знімати позначку придбання, щоб бачити залишок покупок.

- **AC-06-01:** Given false, When purchase PATCH з true, Then 200 і збережено true; наступний запит з false успішно повертає позицію у false.
- **AC-06-02:** Given поточний стан true або false, When повторити його, Then 200 без зміни created_at і кількості позицій; таким чином покриті всі 4 комбінації матриці.
- **AC-06-03:** Given is_purchased=null, рядок "true", число 1 або відсутнє поле, When purchase PATCH, Then 422 і стан попередній.

### US-07 Фільтрація — FR-07

Як користувач, я хочу відбирати позиції за категорією та придбанням, щоб знаходити потрібні товари.

- **AC-07-01:** Given позиції різних категорій і станів, When category_id=1 та is_purchased=false, Then повертаються лише непридбані позиції категорії 1; кожен фільтр також працює окремо.
- **AC-07-02:** Given немає збігів у наявному списку, When фільтр, Then 200 з items=[].
- **AC-07-03:** Given невідома category_id, is_purchased=unknown або повторений query-параметр, When GET наявного списку, Then 422.

### US-08 Статистика — FR-08

Як користувач, я хочу бачити загальний і категорійний підсумок, щоб оцінювати виконання списку.

- **AC-08-01:** Given Молоко 2 л непридбане в категорії 1 та Яблука 1 кг придбані в категорії 3, When статистика, Then total_items=2, purchased_items=1, unpurchased_items=1; категорійні підсумки відповідають позиціям, кількості 2 л та 1 кг не додаються.
- **AC-08-02:** Given порожній список, When статистика, Then 200, три загальні нулі і десять категорій із нульовими значеннями.
- **AC-08-03:** Given виконано фільтр, зміну category_id, позначення або видалення, When наступна статистика, Then вона відповідає всьому поточному списку; суми категорій збігаються із загальними лічильниками.
- **AC-08-04:** Given список не існує, When статистика, Then 404.

### US-09 AI рекомендація — FR-09 — ЛР4

Як користувач, я хочу отримувати семантичну рекомендацію категорії, щоб швидше класифікувати нетипові назви зі збереженням власного вибору.

- **AC-09-01:** Given визначений довідник і контекст Вівсяне молоко без цукру або Кокосове молоко для приготування карі, When запит рекомендації, Then очікуються відповідно категорії 7 та 8; жодна позиція не створюється й не змінюється. Це майбутні перевірки, не отримані зараз результати моделі.
- **AC-09-02:** Given рекомендація категорії 7, When користувач обирає категорію 8 і надсилає звичайний Create/PATCH, Then зберігається саме 8.
- **AC-09-03:** Given текст недостатньо визначений, When рекомендація, Then можливий needs_clarification з null category_id; при відмові адаптера повертається 503, ручне додавання працює.
- **AC-09-04:** Given зафіксовані development/test, словник baseline та конфігурація моделі, When оцінювання, Then обидва методи отримують ті самі 40 test-прикладів, фіксуються accuracy, macro-F1, помилки й час; числовий виграш не припускається наперед.

## 8 Простежуваність і версія

Кожна US-01–US-09 відповідає однойменній FR-01–FR-09. Повний зв’язок усіх 31 AC з компонентами й майбутніми тестами наведений у [traceability.csv](traceability.csv). Покриття поточного обсягу: 8/8 × 100% = 100%. Покриття специфікації з майбутньою FR-09: 9/9 × 100% = 100%; це не означає реалізацію або виконання тестів ЛР4.

Зміни контракту вносяться спочатку сюди, потім у API, критерії й матрицю. Фінальна версія позначається тегом lab01-spec.


## 9 План перевірки семантичної категоризації у ЛР4

**Гіпотеза.** Семантична модель краще визначає категорії контекстних і перефразованих назв, ніж просте зіставлення ключових слів. Перевагу потрібно підтвердити вимірюванням. Власне навчання моделі з нуля не є вимогою.

**Дані.** Перед оцінюванням команда формує синтетичний набір: 20 development-прикладів (по 2 на кожну категорію), 40 test-прикладів (по 4 на категорію) та 5 неоднозначних назв окремо. Поля майбутнього набору: id, split, name, expected_category_id, expected_status. На вході методів — тільки name та довідник; очікувана мітка не передається моделі. Обидва учасники перевіряють розмітку до фіксації набору. Тут задано план і приклади; окремий набір даних не є артефактом ЛР1.

**Приклади для контекстної перевірки.** «Вівсяне молоко без цукру» — 7; «Кокосове молоко для приготування карі» — 8; «Засіб для очищення кухонних поверхонь» — 9; «Щось солодке до чаю» — 10. «Крем» і «Кокосове молоко» без призначення можуть потребувати уточнення. Межі класів визначає довідник розділу 4.3, тому еталонні мітки не є універсальною товарною класифікацією.

**Baseline.** На development формується словник ключових слів для кожної категорії. Назва нормалізується casefold, крайні пробіли видаляються, повторні пробіли стискаються; слова виділяються як послідовності Unicode-літер. Рахуються збіги різних ключових слів із цілими токенами. Повертається єдина категорія з найбільшим додатним рахунком; нуль або рівність максимумів — needs_clarification. До фінального тесту словник заморожується.

**NLP.** Готову модель з підтримкою української мови, спосіб її запуску, prompt і параметри обирають на development. На вхід передаються name та категорії з описами. Вихід — існуюча категорія або needs_clarification. Неправильна структура чи id поза довідником не вважаються успішною відповіддю. Модель і конфігурація фіксуються до test; тайм-аут адаптера — 10 с. Метод не має операції запису товарів.

**Порівняння.** Обидва методи отримують ті самі 40 test-назв. Вимірюються accuracy (правильні категорії / 40), precision/recall/F1 кожного класу, macro-F1 як середнє 10 класових F1, кількість відмов, помилок і технічних збоїв. F1=2PR/(P+R); при нульовому знаменнику — 0. Відмова на рядку з визначеною категорією рахується помилкою. На 5 неоднозначних прикладах окремо рахується частка коректних needs_clarification, вона не входить у macro-F1.

Додатково фіксуються медіана і p95 часу запиту на тому самому стенді; p95 — елемент ceil(0.95*n) впорядкованих вимірів. Час завантаження локальної моделі вимірюється окремо, мережевий час зовнішнього API включається у запит. Для стохастичної моделі виконуються 3 прогони, наводяться результати кожного й середні метрики. Baseline детермінований; час для нього вимірюється за тієї самої кількості повторів.

Результати test не використовуються для доопрацювання словника або prompt у тому самому експерименті. Малий синтетичний набір показує навчальне порівняння, але не доводить перевагу на всіх реальних покупках. Якщо NLP не кращий за baseline, це фіксується як результат. У ЛР1 метрики ще не отримані.
