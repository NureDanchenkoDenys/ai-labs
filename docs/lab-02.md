## Рев'ю першого AI-патча

Перший AI-патч реалізації `POST /lists` збережено тегом `lab02-ai-draft`. За результатами початкової незалежної перевірки отримано `26 passed` у `pytest` та `All checks passed` у Ruff. Описаний нижче стан стосується лише цього першого патча після рев'ю і не є фінальною реалізацією всієї ЛР2.

### Перевірений ризик

Критичне рев'ю `lab02-ai-draft` виявило розбіжність між підрахунком довжини рядка в Python (`len()` після `strip()` у Unicode code points за специфікацією ЛР1) та в SQLite (`length(TEXT)` у `CHECK`-обмеженні таблиць, яка рахує символи лише до першого символу NUL — `\u0000`).

### Регресійні тести

До `tests/test_lists.py` додано регресійний тест `test_create_list_allows_nul_character_in_name` для `POST /lists` із двома значеннями: `{"name": "\u0000"}` і `{"name": "\u0000abc"}`.

- До виправлення два регресійні випадки підтвердили дефект: `2 failed, 26 passed`; обидва запити повернули HTTP `500` (`internal_error`) замість очікуваного `201`.
- Після внесення виправлення виконано самостійну перевірку:
  - `pytest`: `28 passed, 1 warning, 0.70s`;
  - Ruff із правилами `E4,E7,E9,F,I`: `All checks passed`;
  - `git diff --check`: помилок немає;
  - наявність тегу `lab02-ai-draft` підтверджено.

### Прийняті та відкладені рішення

- **Прийнято:** зберегти підтримку символу NUL (`\u0000`) відповідно до специфікації ЛР1, яка не забороняє цей символ і задає обмеження довжини в Unicode code points після `strip()`.
- **Прийнято:** у `app/db.py` виправити `CHECK`-обмеження для `shopping_lists` і `shopping_items` через `length(CAST(name AS BLOB))` (`1–480` та `1–640` байтів відповідно), зберігши точну перевірку довжини в Unicode code points на рівні Pydantic.
- **Прийнято:** залишити доданий регресійний тест у `tests/test_lists.py`.
- **Відкладено:** рефакторинг синхронного SQLite I/O та спільної HTTP-обробки.

### Порівняння AI-draft і версії після рев'ю

| Аспект | `lab02-ai-draft` | Версія після рев'ю |
| --- | --- | --- |
| Маршрути API (`app/main.py`) | Початкова реалізація `GET /health`, `POST /lists` та обробників помилок | Збережено без змін |
| Схеми Pydantic (`app/schemas.py`) | `ShoppingListCreate` (`strip()`, `1–120` Unicode code points) і `ShoppingListResponse` | Збережено без змін |
| Сервісний шар (`app/services.py`) | Формування UTC `created_at` і створення списку | Збережено без змін |
| Схема БД і SQL-запити (`app/db.py`) | Параметризовані запити; `CHECK (length(name) BETWEEN 1 AND 120)` та `BETWEEN 1 AND 160` | Параметризовані запити збережено; `CHECK` змінено на `length(CAST(name AS BLOB))` (`1–480` для `shopping_lists`, `1–640` для `shopping_items`) |
| Тести (`tests/test_lists.py`) | 26 тестів (`26 passed`) | Додано регресійний тест для NUL (`28 passed, 1 warning, 0.70s`) |

### Відомі обмеження

- Старі SQLite-бази автоматично не отримують змінених `CHECK`-обмежень: `CREATE TABLE IF NOT EXISTS` не змінює схему вже існуючої БД без окремої міграції або перестворення файлу бази.
- Перевірка `length(CAST(name AS BLOB))` у SQLite обмежує байтову довжину UTF-8 (`1–480` і `1–640`), тоді як точні межі в Unicode code points (`1–120` і `1–160`) та `strip()` забезпечуються на рівні Pydantic.
- Рефакторинг синхронного SQLite I/O та спільної HTTP-обробки відкладено.

## Оновлення Skill v0 → v1

### Причини оновлення

1. **Надмірне читання контексту:** під час перевірки Skill v0 (позитивні кейси № 1 і № 2) та реалізації `POST /lists` агент читав більше документів і файлів репозиторію, ніж було безпосередньо потрібно для одного функціонального зрізу.
2. **Залишки шаблону Mini Issue Tracker:** у `.agents/skills/tracker-slice/SKILL.md` і `.agents/skills/tracker-slice/references/slices.md` залишалися описи та зрізи іншого проєкту (`POST /issues`, коментарі, `routes.py`, `database.py`, плейсхолдери `<US-xx, AC-xx-yy>`), які не відповідали специфікації ЛР1 «Інтелектуальної системи керування списком покупок» і змушували агента шукати потрібні правила по всій документації.

### Фактичні зміни

- У `.agents/skills/tracker-slice/SKILL.md` оновлено `description`, заголовок, розподіл відповідальності відповідно до фактичної структури (`app/schemas.py`, `app/services.py`, `app/db.py`, `app/main.py`) та перелік обмежень поза обсягом за `docs/requirements.md` (поле `name: tracker-slice` збережено для узгодженості з назвою теки `.agents/skills/tracker-slice`).
- У процедурі й заборонах `SKILL.md` уточнено вибір мінімального контексту: спершу визначити один зріз (A–E) або його погоджену частину, далі читати лише зазначені в `references/slices.md` розділи `docs/` і потрібні файли реалізації/тестів; заборонено безпідставне сканування всього репозиторію, документації й тестів; розширення контексту дозволено лише за конкретної потреби з коротким поясненням причини. Збережено всі попередні правила безпеки, перевірки `pytest` і Ruff, ліміт двох автоматичних спроб виправлення, контроль diff, роль людини в прийнятті змін та обмеження обсягу (`SKILL.md` ≤ 100 рядків).
- У `.agents/skills/tracker-slice/references/slices.md` повністю прибрано залишки шаблону Mini Issue Tracker та описано п’ять фактичних зрізів системи покупок (A — списки й категорії, B — товари, C — видалення та відмітка придбання, D — фільтрація, E — статистика) із посиланнями на фактичні маршрути `API-01`–`API-10`, вимоги `FR-01`–`FR-08` / `NFR-01`, `US-01`–`US-08`, `AC-01-01`–`AC-08-04`, розділи `docs/` та сценарії тестів із `docs/traceability.csv` без дублювання тексту контрактів.

### Очікуваний ефект

Очікується скорочення зайвого читання документів і файлів репозиторію, чіткіша робота в межах одного функціонального зрізу за специфікацією ЛР1 та прозоре пояснення будь-якого розширення контексту. **Ефективність Skill v1 ще не підтверджено експериментально** — для цього потрібні повторні перевірки на практичних запитах.

## Експериментальне порівняння реалізації без AI та з AI

### Мета експерименту

Порівняти самостійну реалізацію без використання AI та реалізацію за допомогою AI на одній і тій самій ізольованій задачі за однаковими вимогами, автоматизованими тестами й перевіркою лінтера. Оцінювалися фактичний час виконання, результати першого прогону тестів і Ruff, кількість ітерацій виправлення, виявлені дефекти, обсяг коду (`loc_code`), а також структура, читабельність і тестованість обох рішень.

### Постановка однакової задачі

Для обох етапів використано єдине заморожене формулювання задачі з `experiments/lr2/task_brief.md` на основі специфікації `docs/requirements.md` (`FR-07`, `BR-04`, `D-05`, `AC-07-01`–`AC-07-03`). Потрібно було реалізувати чисту Python-функцію:

`matches_item_filter(item, *, category_id=None, is_purchased=None) -> bool`

Основні вимоги:
- `item` — коректний словник товарної позиції `ShoppingItem` із полями контракту (додаткова валідація всіх полів позиції не вимагається); функція не повинна змінювати вхідний словник;
- `category_id` (keyword-only, типово `None`) — допустимі `None` або точний тип `int` у діапазоні `1..10` включно; інші типи та значення (зокрема `bool`, числа поза `1..10`, рядки, `float`, контейнери) мають викликати `ValueError`;
- `is_purchased` (keyword-only, типово `None`) — допустимі `None` або точний тип `bool`; інші типи та значення (зокрема `0`/`1`, рядки, `float`, контейнери) мають викликати `ValueError`;
- логіка фільтрації: за відсутності обох фільтрів повертається `True`; за одного фільтра перевіряється відповідність йому; за двох фільтрів застосовується логічне `AND`; неявне змішування `bool` і `int` заборонено; повертається точний тип `bool`;
- ізоляція: без FastAPI, SQLite, мережі, файлової системи та сторонніх залежностей.

### Методика незалежного виконання двох варіантів

1. **Незалежність етапів.** Обидва варіанти створювалися виключно на основі `experiments/lr2/task_brief.md`:
   - `manual-01` (`experiments/lr2/manual_impl.py`) виконано першим, повністю самостійно, без AI-чату й без AI-автодоповнення. Час виміряно від початку написання коду до завершення перевірок: **24 хв 12 с** (`24.2 хв`).
   - `ai-01` (`experiments/lr2/ai_impl.py`) виконано другим у новому чистому сеансі інструмента **Antigravity** (модель за інформацією із сеансу: **Gemini 4 Neon (High)**) без доступу до `experiments/lr2/manual_impl.py`, `tests/test_experiment_lr2.py` та коду `app/`. Час оцінено за хвилинними позначками сеансу: промпт відправлено приблизно о `11:06`, генерацію завершено приблизно о `11:08`, перевірки `pytest` і Ruff завершено приблизно о `11:09`, тобто повна тривалість становила приблизно **3.0 хв**.
2. **Однаковий набір перевірок.** Обидві реалізації перевірялися тим самим набором із **42 тест-кейсів** у `tests/test_experiment_lr2.py` (параметризована фікстура `impl` із варіантами `"manual"` та `"ai"`): робота без фільтрів, фільтрація за `category_id` (включно з межами `1` і `10`), фільтрація за `is_purchased`, 8 комбінацій `AND`, 12 некоректних значень `category_id`, 11 некоректних значень `is_purchased`, 5 змішаних комбінацій валідного й невалідного фільтрів, перевірка keyword-only аргументів (`TypeError`) та відсутності мутації `item`. Під час окремого запуску тестів для одного варіанта інші 42 тест-кейси належали другому варіанту і мали статус `deselected`, а не `failed`. Статичний аналіз виконувався за допомогою Ruff.
3. **Методика підрахунку `loc_code`.** Для обох файлів застосовано однакову методику підрахунку фізичних рядків коду: враховуються всі непорожні рядки Python-коду (імпорти, константи, рядки сигнатури функції, виконувані інструкції та рядки перенесення багаторядкових виразів), за винятком порожніх рядків, коментарів (`#`) та рядків docstring (модульних і функційних):
   - `experiments/lr2/manual_impl.py`: 25 фізичних рядків − 4 порожні рядки − 0 рядків коментарів − 0 рядків docstring = **21** `loc_code`;
   - `experiments/lr2/ai_impl.py`: 57 фізичних рядків − 8 порожніх рядків поза docstring − 0 рядків коментарів − 14 рядків docstring (1-рядковий docstring модуля та 13-рядковий docstring функції) = **35** `loc_code`.
4. **Фіксація часових міток.** Оскільки точний UTC-час проведення етапів не фіксувався, поле `date_utc` у `docs/experiment-lr2.csv` залишено порожнім без підміни датою Git-коміту.

### Аналіз реалізацій за структурою, читабельністю та тестованістю

- **Структура:**
  - `manual_impl.py` (`21` `loc_code`) реалізована максимально компактно без імпортів і модульних констант: спершу валідуються `category_id` та `is_purchased` через вкладені умови `if`, далі обчислюються булеві прапорці `category_matches` і `purchase_matches`, після чого функція має єдину точку виходу `return category_matches and purchase_matches`. Межі `1` і `10` записані безпосередньо в умові, а тип `item` анотований як `dict`.
  - `ai_impl.py` (`35` `loc_code`) використовує іменовані константи `MIN_CATEGORY_ID = 1` і `MAX_CATEGORY_ID = 10`, типізацію `Mapping[str, Any]` (яка приймає будь-яке відображення лише для читання), docstring модуля й функції, валідацію параметрів із комбінованими умовами `and` та стиль раннього виходу (`return False`) для кожного активного фільтра перед фінальним `return True`.
  - Функціонально обидві реалізації однаково коректно захищають від неявного змішування `bool` і `int` як у параметрах фільтра (`type(...) is not int` / `type(...) is not bool`), так і під час порівняння з полями `item["category_id"]` та `item["is_purchased"]`. Помітна дрібна відмінність у потоці керування: у `ai_impl.py` при невідповідності `category_id` функція одразу повертає `False` і не звертається до `item["is_purchased"]`, тоді як у `manual_impl.py` обчислюються обидва прапорці перед кон'юнкцією (для коректного `ShoppingItem` результат ідентичний).
- **Читабельність:**
  - `manual_impl.py` лаконічна, легко прочитується повністю на одному екрані та не перевантажена допоміжними конструкціями; водночас повідомлення винятків дуже короткі (`"Invalid category_id"`, `"Invalid is_purchased"`), а межі діапазону категорій не винесено в константи.
  - `ai_impl.py` містить розгорнутий docstring (`Args`, `Returns`, `Raises`), іменовані константи та інформативніші повідомлення `ValueError`, але має більший обсяг (57 рядків загалом і 35 `loc_code` проти 25 і 21 відповідно) для тієї самої логіки. Більший обсяг документації чи констант сам по собі не робить код об'єктивно кращим: вибір між компактністю та детальним самодокументуванням залежить від стилю й вимог конкретного проєкту.
- **Тестованість:**
  - Обидва варіанти є чистими детермінованими функціями без стану, зовнішніх залежностей і побічних ефектів та підтримують однакову keyword-only сигнатуру, тому мають однаково високу тестованість і перевіряються ідентичними модульними тестами без моків чи інфраструктури.

### Порівняння часу виконання

Фактичний час ручного етапу становив `24.2 хв`, тоді як AI-етап оцінено у `3.0 хв`. Співвідношення часу виконання: `24.2 / 3.0 ≈ 8.07`.

Тобто в межах цього експерименту реалізація з AI разом із перевірками зайняла приблизно у **8.1 раза** менше часу. Оскільки тривалість AI-етапу зафіксована з точністю до хвилин (`11:06–11:09`), фактичне співвідношення має похибку вимірювання і не повинно трактуватися як точна константа. Крім того, час підготовки замороженого `task_brief.md` і тестів не входив у вимірювання жодного з етапів.

### Аналіз виявлених дефектів

В обох реалізаціях (`manual-01` і `ai-01`) усі 42 тест-кейси пройдено з першого запуску (`42 passed, 0 failed`), Ruff не виявив зауважень (`0`), а кількість ітерацій виправлення реалізації дорівнює `0`. Дефектів у Python-коді обох варіантів не виявлено (`defects_found = none`).

Під час перевірки ручної реалізації зафіксовано один процедурний інцидент у терміналі — випадкове склеювання двох команд Ruff в одному рядку. Це є помилкою введення команди, а не дефектом коду Python, тому цей випадок не враховано як ітерацію виправлення реалізації.

### Обмеження експерименту

1. **Масштаб задачі:** досліджувалася лише одна невелика ізольована чиста функція (`matches_item_filter`) без роботи з БД, HTTP-маршрутами чи багатофайловою архітектурою.
2. **Одиночний прогін:** виконано лише по одному прогону для кожного варіанта (`n = 1`), що не дозволяє оцінити статистичний розкид часу та якості.
3. **Попереднє знайомство з предметною областю:** розробник уже був знайомий із вимогами ЛР1 (`FR-07`, `BR-04`, `D-05`), а `task_brief.md` містив чітко формалізовану специфікацію без неоднозначностей.
4. **Точність вимірювання часу AI:** для `ai-01` використано хвилинні позначки (`11:06–11:09`), а не секундомір, і точний UTC-час виконання обох етапів не зафіксовано.
5. **Обмежене тестове покриття:** 42 тест-кейси покривають контрактні сценарії `task_brief.md` для коректного словника `item`, але не перевіряють поведінку на неповних або пошкоджених словниках `item` чи під навантаженням.
6. **Обмежена узагальнюваність:** результати цього експерименту не можна переносити на всі задачі програмування або складніші інтеграційні модулі (що підтверджує попередній розділ звіту про `lab02-ai-draft`, де AI-патч пройшов початкові 26 тестів, але критичне рев'ю виявило розбіжність із SQLite для символу NUL).

### Висновки

- За чітким і недвозначним `task_brief.md` обидві реалізації (`manual-01` та `ai-01`) досягли однакового функціонального й статичного результату з першої спроби: `42/42` тестів пройдено, `0` зауважень Ruff, `0` ітерацій виправлення, дефектів реалізації не виявлено.
- У межах цього експерименту AI-етап (`~3.0 хв`) виявився приблизно у **8.1 раза** швидшим за ручний (`24.2 хв`), з урахуванням хвилинної точності фіксації часу для AI.
- Ручна реалізація є компактнішою (`21` `loc_code`), а AI-реалізація містить більше допоміжних елементів (`35` `loc_code`, іменовані константи, `Mapping[str, Any]`, ранні виходи, docstring і детальніші повідомлення `ValueError`). За фактичними даними жоден із варіантів не можна назвати об'єктивно кращим лише через менший час створення або більший обсяг документації.
- Отриманий виграш у часі стосується конкретної невеликої ізольованої функції за заздалегідь підготовленими вимогами й тестами та не скасовує потреби в незалежному тестуванні й інженерному рев'ю на ширших задачах.
