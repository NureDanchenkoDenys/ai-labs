# Реалізація одного зрізу системи списків покупок

Специфікація ЛР1 у `docs/` (`requirements.md`, `api-contract.md`, `architecture.md`, `traceability.csv`) — єдине джерело правил. Не змінюй її, щоб спростити патч.
Шляхи `docs/`, `app/`, `tests/` — від кореня репозиторію; `references/` — від теки цього Skill.

## Розподіл відповідальності (docs/architecture.md)
- `app/schemas.py` — Pydantic-схеми та перевірка вхідних даних;
- `app/services.py` — бізнес-правила: існування й належність, частковий PATCH, стани придбання, AND-фільтрація, статистика;
- `app/db.py` — збереження в SQLite, `PRAGMA foreign_keys=ON`, транзакції, параметризовані запити;
- `app/main.py` — маршрути FastAPI, перетворення результатів і помилок на HTTP-відповіді.
Розміщуй кожну зміну в шарі, якому вона належить.

## Процедура
1. Визнач один зріз (A–E) або його погоджену частину (один маршрут/підзадачу) за запитом. Якщо запит охоплює кілька зрізів, запропонуй розділити роботу й почни з одного.
2. Відкрий `references/slices.md` і прочитай лише зазначені для обраного зрізу розділи `docs/` та лише потрібні для зміни файли `app/` і `tests/`. Не скануй увесь репозиторій, усю документацію чи сторонні тести; якщо контекст треба розширити, коротко поясни конкретну причину.
3. Перелічи перевірки: критерії приймання `AC-xx-yy` та сценарії тестів із `docs/traceability.csv`, яких стосується зміна.
4. Дай план із 3–5 пунктів і дочекайся підтвердження.
5. Внеси мінімальну зміну лише в дозволених для зрізу файлах разом із тестами для сценаріїв із кроку 3.
6. Перед запуском перевір свій diff: якщо він працює з файлами поза `tmp_path`, з мережею, запускає процеси або видаляє дані — зупинись і дочекайся підтвердження.
7. Запусти перевірки з кореня репозиторію:
   `python -m pytest -q`
   `python -m ruff check app tests --select E4,E7,E9,F,I`
   Якщо щось падає — виправ код і запусти знову. Після двох невдалих спроб зупинись і опиши ймовірну причину: далі діагностує людина.
8. Наведи фактичний підсумок перевірок і окремо — що не зроблено або потребує рішення людини.

## Заборони
- Не скануй безпідставно весь репозиторій, повні файли `docs/` і сторонні тести; розширюй контекст лише за конкретної потреби з коротким поясненням причини.
- Не змінюй маршрути, поля, бізнес-правила й коди відповідей із `docs/api-contract.md` і `docs/requirements.md`.
- Не додавай і не оновлюй залежності; не змінюй налаштування середовища.
- Запускай лише команди перевірки з кроку 7.
- Наявні тести змінюй, лише якщо вони суперечать контракту, і поясни чому; не видаляй перевірки й не пропускай тести, щоб вони пройшли.
- Не додавай функцій поза межами `docs/requirements.md` (розд. 1) і не реалізуй `FR-09` (`API-11`) раніше ЛР4: без реєстрації, автентифікації, ролей, спільних акаунтів, цін, бюджету, оплати, рецептів, історії покупок, видалення або перейменування списків, перенесення позицій між списками, редагування довідника категорій через API та зовнішніх магазинів.
- SQL — лише параметризовані запити з `PRAGMA foreign_keys=ON`; тести — лише на тимчасовій базі (`tmp_path`).
- Не стверджуй, що перевірки пройшли, не запустивши їх. Рішення прийняти зміну — за людиною.

## Формат відповіді
Зріз → прочитані розділи `docs/` і файли (та причина розширення контексту, якщо було) → перевірки (`AC` і тести) → план → diff → підсумок `pytest` і `ruff` → що не зроблено.
